# CSDA Pricing Toolkit — UI/UX Audit Report

**Audit date:** 2 October 2026  
**Reference framework:** [Saeloun — UI/UX Audit Checklist Before Redesign](https://blog.saeloun.com/2025/11/27/ui-ux-audit-checklist-before-redesigning-a-site/)  
**Build reviewed:** Local `csda-toolkit-site/index.html`, service-worker cache `csda-toolkit-v13`

## Executive summary

The toolkit is a capable, visually polished offline application with unusually broad functionality for a single-file build. Its strongest areas are brand consistency, task coverage, responsive CSS, offline operation, and clear primary actions. Its biggest risks are accessibility semantics, information density, the five-second path through some multi-step tasks, a heavy initial HTML payload, and the absence of real behavioral analytics.

**Overall heuristic score: 74/100 — solid, but not yet production-complete for broad public or assistive-technology use.**

| Area from the reference checklist | Score | Status |
|---|---:|---|
| Visual design | 84/100 | Strong |
| Navigation and structure | 79/100 | Good |
| Content clarity | 77/100 | Good, sometimes dense |
| UX and interactions | 73/100 | Good foundation; accessibility debt |
| Mobile experience | 76/100 | Responsive, requires device validation |
| Performance and speed | 68/100 | Fast locally, heavy transfer/parse cost |
| Analytics and user behavior | 30/100 | No evidence available |

> The analytics score is not a visual defect. It reflects that there is no telemetry, heatmap, funnel, or field study from which to validate actual user behavior.

## 1. Audit method and simulation

The reference article recommends reviewing visual consistency, navigation, content, interactions, mobile behavior, performance, and analytics before redesigning. This audit mapped those seven categories to the current application.

### Simulated task flows

The following representative flows were traced through the markup, responsive rules, interaction handlers, and application state logic:

1. **Find a course** — load → splash → category directory/search → course card.
2. **Inspect a course** — select card → focused course outline → proceed to quotation.
3. **Create an enrollment** — student → emergency contact → courses → schedule → payment → agreements → review/finalize.
4. **Administrator workflow** — authenticate → manage catalogue/categories/promos/plans/trainers/enrollments.
5. **Facility rental** — select facility → assign workstation → track session → close/print.
6. **Install/offline workflow** — PWA installation, standalone HTML copy, launcher/icon download.
7. **Resize/orientation scenario** — open focused course panel while moving from desktop width to tablet/mobile width.

### Technical checks

- Local server responses were tested five times.
- Local asset references and duplicate static IDs were checked.
- CSS responsive/reduced-motion rules and JavaScript syntax were inspected.
- Approximate uncompressed and gzip transfer sizes were measured.
- Static form-control and labeling patterns were counted.

## 2. Visual design — 84/100

### What works

- Navy, gold, neutral surfaces, and typography are applied consistently.
- Light and dark themes use centralized variables rather than disconnected colors.
- Cards, tables, forms, notices, and modals share a coherent radius and border system.
- Pricing totals and warnings use strong visual hierarchy.
- Course and PWA artwork is high resolution and now includes transparent PNG, WebP, maskable, touch, and favicon variants.
- Spacing generally scales with `clamp()` and responsive grids.

### Issues

1. **Animation styles accumulated in multiple layers.** Original motion declarations and a later premium override coexist. The computed result is valid, but maintainability is low and future edits can unintentionally revive old behavior.
2. **Visual density is high in enrollment and administration panels.** Numerous boxes, pills, borders, notes, and warnings can compete for attention.
3. **Persistent decorative glints may become visual noise.** The sweeping highlights on cards and buttons are attractive in isolation but frequent across a dense catalogue.
4. **Several visual states rely on color.** Some warning/selected states include text or borders, but a systematic non-color cue is not guaranteed everywhere.

### Recommendation

Consolidate all motion into one definitive section and reduce decorative animation frequency. Reserve glints for the primary CTA or first-run discovery, not every repeated surface.

## 3. Navigation and structure — 79/100

### What works

- The two primary jobs — **Enroll Student** and **Facility Rental** — are prominent.
- Category navigation, live counts, and search support course discovery.
- Search has a keyboard shortcut and clear action.
- Enrollment is divided into named tabs instead of one extremely long form.
- Admin functions are grouped into tabs.
- Important actions are generally reachable within one to three interactions.

### Issues

1. **The application has several parallel navigation models:** category directory, course-card focus view, quotation tabs, enrollment tabs, admin tabs, and modal panels. This is appropriate for scope but increases cognitive load.
2. **Tab selection is visually animated but not implemented as a true semantic tab system.** Buttons do not consistently expose `role="tab"`, `aria-selected`, and associated `tabpanel` relationships.
3. **Closing behavior differs across panels.** Escape, close buttons, guarded enrollment panels, backdrop clicks, and course-card exits do not all behave identically.
4. **Admin discoverability depends on a gear button and password knowledge.** This is acceptable for staff, but the state and audience could be clearer.

### Recommendation

Standardize navigation semantics and closure behavior. Add a visible step count such as “Step 3 of 6” to enrollment, not just tab names and status dots.

## 4. Content clarity — 77/100

### What works

- Course names, prices, hours, schedules, discounts, payment stages, and late-payment figures are explicit.
- Primary CTAs use action-oriented labels.
- Notices explain why a rule exists instead of showing only an error.
- Printed enrollment and rental documents use clear sections and totals.
- Compliance and privacy messaging is integrated into the relevant workflow.

### Issues

1. **Some helper copy is too long for transactional moments.** Users completing enrollment may scan past paragraphs about scheduling, phone verification, installation, or payment handling.
2. **Terminology varies between “guardian,” “emergency contact,” “parent/legal guardian,” and “contact person.”** These concepts overlap but are not always identical.
3. **Several screens contain multiple competing CTAs.** For example, save, finalize, print, email, and copy-summary actions can appear within the same completion stage.
4. **Error messages are primarily toast-based.** A toast can disappear before the user finds the field that needs correction.

### Recommendation

Use progressive disclosure: one-sentence guidance by default, with “Why?” or “Learn more” expansion for detailed policy. Pair every validation toast with persistent inline field guidance.

## 5. User experience and interactions — 73/100

### What works

- Buttons, cards, inputs, and selectable panels provide tactile feedback.
- The focused course view now hides the source card, blurs the backdrop, and preserves the grid footprint.
- Opening and closing motion uses a zero-bounce premium curve.
- The source card fades back into the grid during exit.
- Reduced-motion support is present and placed after premium overrides.
- Form state is preserved when changing enrollment tabs.
- Scheduling logic handles skipped dates, holidays, manual adjustments, and date ranges.

### High-impact issues

1. **Form label association is the largest accessibility defect.** The source contains 97 labels but only one explicit `for=` relationship. Many inputs rely on visual proximity rather than programmatic association.
2. **Custom checkbox-like controls are `<div>` elements.** They may not be keyboard-focusable or announced as checkboxes unless corresponding roles, tabindex, key handlers, and `aria-checked` states are applied.
3. **Focus management is incomplete.** Modals receive focus in selected places, but there is no clear universal focus trap or guaranteed restoration to the launch control.
4. **Dynamic status announcements are inconsistent.** Toasts and state changes may not be exposed through `aria-live`.
5. **Long modal content can create focus/scroll complexity.** Sticky regions help visually, but assistive-technology order should be tested.
6. **The course interaction remains motion-heavy for a frequent action.** The current 650 ms open plus backdrop transition is deliberately cinematic; repeated course comparison may feel slow.

### Recommendation

Run a dedicated WCAG 2.2 AA pass before public release. Start with labels, custom controls, modal focus trapping/restoration, live regions, and keyboard-only completion of enrollment.

## 6. Mobile experience — 76/100

### What works

- The primary two-column catalogue collapses to one column.
- Category controls become a wrapping horizontal set.
- Modals become bottom sheets below 640 px.
- Focused course panels use dynamic viewport height and safe margins.
- Tables and session controls have mobile-specific sizing.
- Typography and grids use responsive sizing.

### Issues

1. **Dense tables remain challenging below 390 px.** Session schedules, payment tables, and verification tables can force horizontal compression.
2. **Some controls are below the ideal 44×44 CSS-pixel touch target.** Examples include 21–29 px day, close, and icon controls.
3. **A five-second splash is no longer present, but even the restored three-second splash delays task access.** Repeat users should not be forced through it on every launch.
4. **The 828 KB single HTML document requires parsing before interaction.** Mid-range mobile devices may show longer startup cost than the local server test suggests.
5. **Backdrop blur is GPU-intensive.** A 12 px blur over the whole viewport can affect lower-end mobile devices.

### Recommendation

Use a one-time or first-session splash, increase all touch targets to at least 44×44 px, and provide compact/card alternatives for wide tables on small screens.

## 7. Performance and speed — 68/100

### What works

- No frameworks, remote fonts, third-party scripts, analytics bundles, or runtime API calls.
- Local responses are effectively instantaneous.
- Service-worker caching supports offline use.
- WebP icon variants exist.
- Catalogue cards use `content-visibility:auto`.

### Issues

1. **The HTML grew to 828 KB, approximately 439 KB gzip.** Embedding the transparent CPT PNG directly contributed significantly.
2. **All application logic, default data, styles, and large image constants are parsed as one document.** This improves portability but increases initial parse/compile work.
3. **Repeated or superseded CSS motion rules increase stylesheet size and debugging cost.**
4. **The service-worker cache requires manual version bumps.** Missed bumps can preserve stale visual behavior.
5. **Animated full-screen blur and many simultaneous glints can increase paint/compositing work.**

### Recommendation

For the hosted build, externalize icons and optionally JavaScript/CSS while retaining a separate downloadable single-file edition. Automate cache versioning from a content hash. Measure production Core Web Vitals on the actual Vercel deployment.

## 8. Analytics and user behavior — 30/100

The reference framework recommends heatmaps, bounce/exit rates, session duration, conversion paths, and mobile-vs-desktop comparisons. The toolkit intentionally has no analytics, and no usability-session data was provided.

### Consequences

- It is not possible to verify where users abandon enrollment.
- Course-card usage and search success cannot be measured.
- The effect of the splash, animations, warnings, or form length is unknown.
- Mobile/desktop task differences are assumptions rather than observed behavior.

### Privacy-conscious measurement plan

Because enrollment data is sensitive, avoid recording field values or personal information. If measurement is introduced, collect only anonymous events such as:

- `course_search_started`
- `course_outline_opened`
- `quote_started`
- `enrollment_tab_viewed`
- `validation_blocked` with non-sensitive reason code
- `enrollment_completed`
- `rental_started` / `rental_completed`

Prefer aggregated, consented, self-hosted telemetry or structured staff observation over session replay on enrollment screens.

## 9. Prioritized roadmap

### P0 — Before production use

1. Associate every form control with a real label.
2. Convert custom checkboxes/radios/tabs to semantic controls or add complete ARIA and keyboard behavior.
3. Implement modal focus trap, initial focus, Escape policy, and focus restoration.
4. Add persistent inline validation tied to fields with `aria-describedby`.
5. Confirm sensitive enrollment data retention, backup, and device-access policy.

### P1 — High-value UX improvements

1. Increase small touch controls to 44×44 px.
2. Make the splash first-run-only or reduce it substantially for returning users.
3. Simplify enrollment instructions through progressive disclosure.
4. Consolidate the duplicated motion/CSS system into one source of truth.
5. Replace wide mobile tables with stacked cards or controlled horizontal scrolling.
6. Run five moderated tests: two enrollment staff, one administrator, one trainer, one mobile-first user.

### P2 — Performance and refinement

1. Split hosted assets while preserving a downloadable standalone build.
2. Automate service-worker cache hashes.
3. Pause decorative glints when surfaces are off-screen or after first interaction.
4. Measure Vercel production performance with Lighthouse/PageSpeed and real devices.
5. Introduce privacy-safe funnel events only after consent and governance review.

## 10. Suggested usability test script

Ask each participant to complete these tasks without coaching:

1. Find a course related to “anatomy” and state its price and duration.
2. Compare it with two other courses and identify the best available discount.
3. Start an enrollment for an adult learner and reach the review screen.
4. Change the schedule start date and remove one session.
5. Record a partial payment and explain the remaining balance.
6. Return to the catalogue and locate the same course again.
7. On mobile, repeat tasks 1–3 using one hand.
8. For staff, export a backup and explain how it would be restored on another computer.

Capture completion, time on task, errors, backtracking, assistance requests, and one post-task confidence score from 1–5. Do not collect real student information during testing.

---

## Conclusion

The current product should be refined rather than redesigned from scratch. Its information architecture and functional coverage are valuable. The best next investment is not another visual overhaul; it is accessibility remediation, mobile touch ergonomics, content reduction, production performance measurement, and real-user task testing. Those steps directly follow the reference article’s central principle: audit first, then improve based on evidence rather than preference.
